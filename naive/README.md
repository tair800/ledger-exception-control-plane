# `naive/` — the RED baseline

This directory holds a **deliberately unsafe** implementation of the same job `src/` does. It exists
for one reason, stated in [`PROJECT_SPEC.md` §19](../PROJECT_SPEC.md):

> `naive/` — a deliberately unsafe baseline: no idempotency key, no outbox, no claim locking. **It
> must double-post.**
>
> `main` — the real implementation. **It must not.**
>
> A suite that passes on both branches proves nothing and is a defect.

Without this directory the chaos suite is theatre. A green result on `main` alone says nothing about
whether the faults were injected, whether the assertions can fail, or whether the reliability layer
is doing any work — and increment 4.5 is the gate that refuses to accept the flagship claim on
those terms.

## It is not a straw man

The point of a RED baseline is only made if the baseline is what a competent engineer would
*actually write*. Every line here is code somebody would ship having simply not thought about
duplicate financial side effects yet:

- work is claimed with `SELECT … WHERE state = 'open'` and then updated — the obvious two-step;
- the adjustment row is inserted and the posting sent, in that order, each in its own transaction —
  which is what you get when you write the two statements you need;
- a failed send is retried, because retrying a failed request is ordinary good practice;
- the posting carries a fresh request identifier per attempt, because that is what an identifier is
  *for* when nobody has asked the provider to deduplicate on it.

There is no sabotage. Nothing sleeps, nothing double-writes on purpose, no counter is nudged, and no
assertion is helped along. **Every failure this baseline exhibits is a failure of omission**, and
each omission has a name in `src/`:

| Missing here | Present in `src/` | Increment |
|---|---|---|
| A retry-independent operation identifier | `operations/identity.py`, `adjustment.operation_id` unique | 4.1 |
| A claim that two workers cannot both take | `operations/claim.py`, `SELECT … FOR UPDATE SKIP LOCKED` | 4.1 |
| The state change and the dispatch intent in one transaction | `operations/service.py`, the `outbox` table | 4.2 |
| A write-ahead record committed before the socket write | `posting_attempt` | 4.2 |
| An outcome vocabulary that can say *"I do not know"* | `ledger/port.py`'s five-valued `PostingOutcome` | 4.2 |
| A retry that only ever takes a failure it can prove wrote nothing | `operations/retry.py`, the transport classifier | 4.3 |
| Anything at all that resolves an ambiguity | `operations/reconcile.py`, `operations/recovery.py` | 4.4 |
| A content-hash unique constraint on ingestion | `settlement_batch.content_hash` | 2.1 |
| Single-use approval tokens | `uq_approval_token` | 5.1 |

## It runs under the same conditions

The comparison is only worth anything if both branches face the same world, so this baseline uses
**the same ledger adapters, the same three capability configurations and the same fault-injection
port** as `src/`. It imports those and nothing else. It shares no reliability code, no schema and no
transaction discipline.

It has its own tables — `naive_*`, created by `naive/schema.py` rather than by a migration — and that
is not a convenience. `src/`'s schema *itself* prevents the defect: `adjustment.operation_id` is NOT
NULL and unique, so a naive implementation writing into main's tables would be protected by main's
constraints and the baseline would show no failure at all. Letting that happen would be rigging the
comparison in the other direction.

## Nothing in `src/` may import this

A guard test enforces it. The dependency runs one way only: this baseline may read the ledger port,
the reference adapters and the fault vocabulary; the shipped system may not know this directory
exists.

## Results

The scenario-by-scenario table produced by the chaos suite is in the
[README](../README.md#chaos-suite-results), generated by `make chaos-table` from a run against real
PostgreSQL. Every number there is the simulated ledger's own applied-count, recorded by the scenario
that drove it.

Two rows of that table are worth reading closely, because neither is a duplicate and neither has
been written up as one. **Worker killed mid-batch** loses this baseline its work rather than
duplicating it — the batch is claimed up front and committed, so the work is stranded rather than
re-claimable, which is a different defect. And an **ambiguous 5xx** leaves this baseline *correct by
luck*: nothing had been applied, so its retry completed the work once, on the identical inference
that double-posts when a response is lost after a commit.
